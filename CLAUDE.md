**Phase 4 — complete (2026-08-23), via polling instead of webhooks:** Goal was automatic redeployment on push. Started down the GitHub-webhook path (per-stack Portainer webhook URL registered as a GitHub repo webhook via the API) but hit a hard blocker on the very first one (`crashplan`): Portainer's webhook URL is `https://portainer.local.nelsonhickman.com/api/stacks/webhooks/...`, a hostname that only resolves inside the LAN via Pi-hole. GitHub's webhook delivery servers are on the public internet and can't reach it — confirmed via a ping delivery that failed with "failed to connect to host" / `502`. That webhook was deleted (GitHub webhook id `669257685`) rather than left registered and silently broken. Exposing just the webhook path publicly (e.g. via a Cloudflare Tunnel route) was considered but not pursued — not needed given the alternative below.

Instead, all 23 stacks (both hosts) already had Portainer's built-in Git **polling** ("automatic updates" with a fetch interval, not a webhook) enabled during Phase 3 as each was connected — 5 minutes for every stack except `days-since-incident`, which was set to several hours (fine as-is; that stack's data barely changes). This already satisfies the "auto-redeploy on push" goal, just with up to a 5-minute lag instead of instant.

Checked whether 5 minutes × 23 stacks against one repo risks GitHub rate-limiting, since GitHub's unauthenticated REST API is capped at 60 requests/hour/IP and 23 stacks × 12 polls/hour = 276 checks/hour would blow through that if it used the REST API. Confirmed empirically it doesn't: nelson-nuc's IP still had 58/60 of its REST quota (`api.github.com/rate_limit`) unused despite hours of live polling across all stacks, and 6 hours of Portainer's own logs had zero rate-limit/403/429 errors related to Git checks. Portainer's polling uses git's smart-HTTP protocol (the same lightweight check `git ls-remote` does) rather than the REST API, which is a separate and far more generous limit bucket for anonymous access — so 5-minute intervals are safe and don't need to be lengthened. The one structural inefficiency is that 23 independent stacks each poll the *same* repo on their own unsynchronized timer rather than one shared check fanning out to all — Portainer has no mechanism to consolidate this, and at this scale it isn't worth working around.

**Lesson for future stacks:** don't assume a Portainer webhook URL is reachable from GitHub just because it's reachable from inside the LAN — `*.local.nelsonhickman.com` never will be. If a future service specifically needs instant (not polled) redeploy, the path would be exposing just that webhook route through the existing `cloudflared` tunnel, not the general GitHub-webhook setup used here.

## Portainer migration research (2026-09-11, planning only — no infra changed)

Portainer announced 3.0 will be Kubernetes-first, with Docker/Swarm support frozen (no new policy-management or observability features going forward, though still functional). Confirmed directly from [Portainer's own 3.0 announcement post](https://www.portainer.io/blog/portainer-3-0-is-coming), the actual shape is more nuanced than a flat "CE is gone": **2.x CE stays supported indefinitely on a security-patch/selective-backport basis** — 2.45 is the last LTS, and staying on 2.x is described by Portainer itself as "a supported decision." What's actually going away is a **separate free CE build going forward** — 3.x ships only as the Business Edition, with community access via a capped "3 Nodes Free" program rather than a FLOSS release. That distinction matters for the urgency read: this isn't "Portainer stops working in 6 months," it's "the free tier stops being FLOSS and stops getting new features as of now, and the 2.x security-patch runway is finite" — worth re-confirming the actual 2.x EOL date before treating 6 months as a hard drop-dead if it becomes important later (the user's stated 6-month figure was not independently re-verified against a specific EOL announcement date during this research pass).

Alternatives evaluated against the hard requirements (multi-host, GitOps/IaC, FLOSS with no feature gating, self-hostable):
- **[Komodo](https://github.com/moghtech/komodo)** (GPL-3.0, confirmed via its repo's `LICENSE` file) — top pick. Core + Periphery architecture (stateless per-host agent, central Core service talking to Mongo/FerretDB/Postgres). Purpose-built for exactly this repo's pattern: git-tracked Docker Compose stacks across multiple servers, no paywalled multi-host or GitOps functionality. Added a dedicated Docker Swarm resource type in 2026; still Docker/Compose-first, not a Kubernetes tool. v2 switched from passkey auth to Ed25519 PKI keypairs — worth reading current docs at POC time since this is a fast-moving young project.
- **[Coolify](https://github.com/coollabsio/coolify)** (Apache-2.0, confirmed via its repo's `LICENSE` file) — strong alternative, broader PaaS feature set (280+ one-click services, S3 backups, multi-server over plain SSH, push-to-deploy), also exploring Kubernetes support. More opinionated/heavier than this repo's current per-stack-compose-file model; would nudge toward Coolify's own app-deployment abstraction rather than a straight compose-stack sync.
- **CapRover** (Apache-2.0) — good GUI, git-deploy, built-in Swarm-based multi-host clustering. Same category problem as Coolify: app-hosting/PaaS-centric, an awkward fit for arbitrary third-party compose stacks (media server, home automation, etc.) the way this repo is structured, so ranked below Coolify.
- **k3s + ArgoCD/Flux** (both CNCF projects) — the actual gold-standard FLOSS GitOps combo, and the natural path for the "experiment with Kubernetes" nice-to-have, but requires rewriting every stack as Kubernetes manifests/Helm charts. Treated as a separate, later, deliberate migration — not part of the Portainer-exit timeline.

## Komodo POC: steps 4–9 completed (2026-09-13/14)

Findings worth keeping at this level because they'd otherwise be re-discovered the hard way on any future Komodo work:

- **Komodo Core's HTTP login route isn't in its own published API docs.** Had to `curl` Core's own minified frontend JS bundle and grep it to find the real path: `POST /auth/login/{LoginType}` (e.g. `/auth/login/LoginLocalUser`) with the body as bare `{username, password}` — *not* the `{"type", "params"}` envelope that `/read`, `/write`, and `/execute` all use. **SQLite gotcha, found while testing:** the script runs `sqlite3` as the DB file's owner so a `-wal`/`-shm` it creates isn't root-owned. Tested with throwaway containers (Postgres, plus WAL-mode SQLite in both a bind mount and a named volume): all dumps restored, and no root-owned files or leaked mounts were left.
