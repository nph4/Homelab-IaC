**Phase 4 — complete (2026-08-23), via polling instead of webhooks:** Goal was automatic redeployment on push. Started down the GitHub-webhook path (per-stack Portainer webhook URL registered as a GitHub repo webhook via the API) but hit a hard blocker on the very first one (`crashplan`): Portainer's webhook URL is `https://portainer.local.nelsonhickman.com/api/stacks/webhooks/...`, a hostname that only resolves inside the LAN via Pi-hole. GitHub's webhook delivery servers are on the public internet and can't reach it — confirmed via a ping delivery that failed with "failed to connect to host" / `502`. That webhook was deleted (GitHub webhook id `669257685`) rather than left registered and silently broken. Exposing just the webhook path publicly (e.g. via a Cloudflare Tunnel route) was considered but not pursued — not needed given the alternative below.

Instead, all 23 stacks (both hosts) already had Portainer's built-in Git **polling** ("automatic updates" with a fetch interval, not a webhook) enabled during Phase 3 as each was connected — 5 minutes for every stack except `days-since-incident`, which was set to several hours (fine as-is; that stack's data barely changes). This already satisfies the "auto-redeploy on push" goal, just with up to a 5-minute lag instead of instant.

Checked whether 5 minutes × 23 stacks against one repo risks GitHub rate-limiting, since GitHub's unauthenticated REST API is capped at 60 requests/hour/IP and 23 stacks × 12 polls/hour = 276 checks/hour would blow through that if it used the REST API. Confirmed empirically it doesn't: nelson-nuc's IP still had 58/60 of its REST quota (`api.github.com/rate_limit`) unused despite hours of live polling across all stacks, and 6 hours of Portainer's own logs had zero rate-limit/403/429 errors related to Git checks. Portainer's polling uses git's smart-HTTP protocol (the same lightweight check `git ls-remote` does) rather than the REST API, which is a separate and far more generous limit bucket for anonymous access — so 5-minute intervals are safe and don't need to be lengthened. The one structural inefficiency is that 23 independent stacks each poll the *same* repo on their own unsynchronized timer rather than one shared check fanning out to all — Portainer has no mechanism to consolidate this, and at this scale it isn't worth working around.

**Lesson for future stacks:** don't assume a Portainer webhook URL is reachable from GitHub just because it's reachable from inside the LAN — `*.local.nelsonhickman.com` never will be. If a future service specifically needs instant (not polled) redeploy, the path would be exposing just that webhook route through the existing `cloudflared` tunnel, not the general GitHub-webhook setup used here.

**`adventurelog` was unreachable from outside the LAN, root cause was outside this repo entirely (2026-08-29):** the Traefik router label was already correctly pointed at the public hostname (`Host(\`adventurelog.nelsonhickman.com\`)`, commit `6b0ecad`), but that only makes Traefik *ready* to route the host once traffic arrives — nothing was actually forwarding public traffic there. `cloudflared`'s ingress rules are configured remotely in the Cloudflare dashboard/API (its compose file just runs `tunnel --no-autoupdate run` with no local ingress config), and the live tunnel config (confirmed via `docker logs cloudflared`'s "Updated to new configuration" line, then directly via the Cloudflare API) only had `mealie.nelsonhickman.com` and `nextcloud.nelsonhickman.com` — `adventurelog` had never been added. Public DNS confirmed the same gap: `adventurelog.nelsonhickman.com` had no DNS record at all (unlike `mealie`, which resolves to Cloudflare's proxy IPs), so it wasn't even reaching Cloudflare's edge from outside. It "worked" on the LAN only because Pi-hole resolves the bare (non-`.local`) hostname locally to Traefik's LAN IP — a local override with no public equivalent, which is exactly what made the gap invisible from the LAN side.

Fixed via the Cloudflare API (using the `cloudflare` Claude Code plugin, `mcp__plugin_cloudflare_cloudflare-api__execute`, authenticated via OAuth): added an ingress rule for `adventurelog.nelsonhickman.com` → `https://traefik:443` (same `httpHostHeader`/`originServerName` pattern as the existing `mealie` entry) to tunnel `docker` (`cbdf54c2-ed28-4198-836b-cd86075a06fc`), and created a proxied CNAME `adventurelog.nelsonhickman.com` → `cbdf54c2-….cfargotunnel.com` in the `nelsonhickman.com` zone, matching the existing `mealie`/`nextcloud` DNS records exactly. Confirmed via `curl --resolve` straight to Cloudflare's proxy IP (bypassing local DNS-cache propagation lag): `200`. No repo changes were needed — this was purely Cloudflare account-side config that the repo has no representation of at all.

**Lesson for future public-facing services:** a Traefik `Host()` label targeting a bare `*.nelsonhickman.com` hostname is necessary but not sufficient for external reachability — it also needs a matching Public Hostname entry in the Cloudflare Tunnel config (dashboard, or API via the `cloudflare` plugin) and a DNS record, neither of which live in this repo or show up from reading it. Pi-hole's local override for the same non-`.local` hostname can make a misconfigured service look fully working when tested from the LAN, hiding the gap until someone tries it from outside — so a new public hostname should always be smoke-tested from outside the LAN (e.g. via `curl --resolve <host>:443:<cloudflare-proxy-ip>`, or cellular data) before being considered done, not just checked via the browser at home.
