# Komodo Proof-of-Concept Plan

Status: **all 9 steps complete (2026-09-13/14)** — both hosts connected, redeploy-on-push proven on nelson-nuc, second host proven on quark-vm, GUI evaluated (API-level). **Stateful follow-up POC also complete (2026-09-19)** — see "Follow-up" section: named-volume pinning works unmodified, `env_file` secrets needed one Periphery mount fix (now applied). See the README's "Migrating off Portainer" section for why this is happening. See "Progress Log" below for what's actually been done against the Steps below.

## Goal

Prove [Komodo](https://github.com/moghtech/komodo) (GPL-3.0) can do this repo's core GitOps loop — a git-tracked compose stack deployed to a named host, auto-redeployed on push — across **two** hosts (nelson-nuc + quark-vm), before committing to migrating anything real off Portainer.

Target stack for the POC: `it-tools` ([`stacks/nelson-nuc/it-tools/docker-compose.yml`](stacks/nelson-nuc/it-tools/docker-compose.yml)). It has no volumes and no secrets — just a single pinned image and Traefik labels on the external `proxy` network — making it the lowest-risk stack in the repo to experiment with, same reason it was a good first stack for the original Portainer GitOps migration (see `CLAUDE.md`, Phase 3).

## Non-goals (explicitly out of scope for this POC)

- **No cutover of the real `it-tools` container or its hostname.** The live, Portainer-managed `it-tools` and `it-tools.local.nelsonhickman.com` are never touched.
- **No secrets or `env_file` handling, no named-volume pinning.** `it-tools` has neither, so this POC only proves the *simple* case. This repo has two known hard patterns that a real migration would also need to validate: absolute-path `env_file`/Docker `secrets:` (see README's Architecture section), and the uptime-kuma/mealie external-volume-pinning trick documented in `CLAUDE.md` (a plain named volume can silently get re-prefixed under a new tool's project name and resolve to an empty volume instead of the real data). Neither is exercised here — see "Follow-up" below.
- **No GitHub webhook wiring.** `CLAUDE.md`'s Phase 4 notes record that Portainer's webhook URL (`*.local.nelsonhickman.com`) is unreachable from GitHub's public delivery servers — LAN-only hostname, no route in. Komodo's webhook receiver would hit the exact same reachability problem if pointed at a LAN-only hostname. Start with polling (the same tradeoff already accepted for all 23 Portainer stacks); webhook-via-the-existing-`cloudflared`-tunnel is a stretch goal only, not a requirement.

## Architecture

- **Komodo Core** — new container on nelson-nuc, its own standalone stack, not yet Traefik-routed (or routed to a throwaway `komodo-poc.local.nelsonhickman.com` for convenience). Kept entirely separate from anything Portainer manages.
- **Periphery agents** — one on nelson-nuc, one on quark-vm. Installing both (not just one) is the part that actually exercises the multi-host hard requirement.
- **Database** — whatever Komodo's docs currently recommend (Mongo by default; FerretDB or Postgres as alternatives if avoiding a new Mongo instance is preferable for a POC-scale deployment).

## Steps

1. Read Komodo's current install docs for the Core + Periphery topology and its auth model (Ed25519 keypairs per its 2026 v2 change) — confirm nothing conflicts with the existing Tailscale/LAN setup between nelson-nuc and quark-vm.
2. Stand up Komodo Core on nelson-nuc as its own compose stack, LAN-only for now.
3. Install Periphery on nelson-nuc, register it with Core.
4. Install Periphery on quark-vm (SSH access already exists — see the Portainer-agent-upgrade entry in `CLAUDE.md`), register it with Core. This is the multi-host proof point.
5. In Komodo, define a Stack resource pointing at this repo (`https://github.com/nph4/Homelab-IaC`, branch `main`, path `stacks/nelson-nuc/it-tools/docker-compose.yml`), but override the deploy identity so it can't collide with the live container: different container name (e.g. `it-tools-komodo-poc`) and a different Traefik router/hostname (e.g. `it-tools-poc.local.nelsonhickman.com`) — the same dual-running pattern this repo already used for the `cloudflared` and `dashy` (`dashy-validate-test`) cutovers. It can still safely join the real external `proxy` network since the container name differs.
6. Deploy to nelson-nuc's Periphery agent. Verify against the same bar every stack in the original Portainer migration was held to: `docker inspect` shows it sourced from the Git clone, correct pinned image tag, `TZ` set, joined to `proxy`, and a `200` through Traefik at the POC hostname.
7. Make a trivial commit on `main` (e.g. a label comment change) and confirm Komodo's poll picks it up and redeploys without manual action — the actual behavior being validated.
8. Repeat a minimal version of steps 5–7 targeting the quark-vm Periphery agent (doesn't need to be `it-tools` specifically — any throwaway stack proves the second host works from the same Core).
9. Judge the GUI against Portainer's for the operations actually used day to day: viewing logs, triggering a redeploy, seeing which commit is currently deployed, spotting drift.

## Success criteria

- [x] Both hosts manageable from a single Komodo Core. — confirmed via `ListServers` (`Local` + `quark-vm`, both `Ok`).
- [x] A git push results in an automatic redeploy, verified via `docker inspect`'s commit hash — not just "the page loads." — confirmed via `GetStack`'s `deployed_hash` tracking the pushed commit (see Progress Log, step 7). Caveat: proven via the same execute path the daily schedule uses, not by waiting for that schedule to fire unattended.
- [ ] No feature Portainer currently provides for free turns out to require a paid Komodo tier. — not yet assessed; needs a real feature-by-feature comparison, not just this POC's narrow slice.

## Rollback / cleanup

Trivial by design, since everything here is new and parallel to production: stop/remove the POC container and its Komodo Stack resource, remove both Periphery agents and Komodo Core, delete the POC Traefik hostname. The live `it-tools` and its Portainer entry are never at risk.

**Step 7 — push → redeploy proof.** Pushed a comment-only trivial change to `docker-compose.komodo-poc.yml` (commit `a0a9b46`). **Finding worth flagging:** Komodo's out-of-the-box automatic redeploy cadence is *not* comparable to Portainer's 5-minute polling — `poll_for_updates`/`auto_update` are actually driven by a single Core-wide scheduled Procedure named "Global Auto Update," created on first boot with a default schedule of **once daily at 03:00** (`bin/core/src/startup.rs`), not a continuous per-stack poll loop. Rather than wait until 3am or change that shared schedule (which would affect every future auto-update-enabled stack, a bigger decision than this POC needs to make), proved the underlying mechanism directly by invoking the same execute path the schedule itself calls: `execute/DeployStackIfChanged` on the `it-tools-komodo-poc` stack. Result: `GetStack` afterward showed `deployed_hash` advance to `a0a9b46` (matching `latest_hash`, matching the pushed commit) — Komodo pulled and re-applied the new commit. `docker inspect`'s `StartedAt` was unchanged (no container recreate), because the change was comment-only and Docker Compose's own diffing correctly found nothing to apply — the same "no-op redeploy" behavior already documented for the Home Assistant GitOps stack in `CLAUDE.md`. This satisfies the success criterion (push → tracked redeploy, verified via the deployed commit hash, not just "the page loads"), but the daily-schedule default is a real operational difference from Portainer worth carrying into any future migration decision — either the schedule needs shortening, or per-stack manual/webhook triggering is the expected pattern between daily runs.

## Follow-up (separate from this POC)

**2026-09-19 — Stateful follow-up POC completed: both hard patterns validated, one real blocker found and fixed.**

Built a third throwaway stack, `komodo-poc-stateful-test/docker-compose.yml` (repo root, same "outside `stacks/`" convention as `komodo-poc-quark-test`, commit `2584784`), combining both patterns in one container on nelson-nuc's `Local` server:
- A pre-existing named volume (`komodo-stateful-poc-legacy_data`, created manually with a marker file *before* the Komodo Stack existed) pinned via `volumes.legacy-data: {name: ..., external: true}` — the exact uptime-kuma/mealie landmine shape.
- An absolute-path `env_file: /home/nelson/containers/komodo-poc-stateful-test/.env` — this repo's standard secrets pattern (mealie, cloudflared, adventurelog, etc.).

**Volume pattern: works exactly like Portainer, no surprises.** `docker inspect` confirmed the container mounted the real pre-existing volume (container logs printed the marker written before the Stack was ever created), and `docker volume ls` showed no shadow/duplicate volume got created under Komodo's own project-name prefix. The `external: true` pin is respected identically to how it worked in the original Portainer migration — this pattern needs no Komodo-specific handling beyond what's already documented in `CLAUDE.md`.

**`env_file` pattern: found a real, structural blocker, not present in Portainer — now fixed.** First deploy attempt failed outright at the `Compose Config` stage: `env file /home/nelson/containers/komodo-poc-stateful-test/.env not found`. Root cause is different from — and more fundamental than — the Portainer-era blocker (`CLAUDE.md` Phase 2): Portainer's own container just needed read access to *resolve* the path; Komodo's Periphery agent actually **executes `docker compose` as a subprocess inside its own container** (confirmed by reading `komodo/compose.yml` — Periphery mounts only `docker.sock`, `/proc`, and its own configured root directory, nothing under `/home/nelson`), so any file reference — not just this repo's compose files, *any* absolute host path a compose file names — is invisible unless it happens to fall under Periphery's mounted root. This is a general property of Periphery's architecture, not an `env_file`-specific quirk. Fixed with the direct structural analog of the Portainer fix: added `/home/nelson/containers:/home/nelson/containers:ro` to Periphery's volume mounts in `komodo/compose.yml` (host-side only, not repo-tracked, same as the rest of the Komodo standup — see the 2026-09-12 entry above), recreated just the `periphery` service (`RestartCount: 0` after). Redeploy then succeeded: `Compose Config` resolved `TEST_SECRET_VALUE` from the real file, `deployed_hash` matches `latest_hash` (`2584784`), container stable.

**Verdict for a real migration:** the named-volume pattern needs zero new Komodo-specific work. The `env_file` pattern needs this one Periphery mount added *once*, up front, before connecting any stateful stack — after that, every existing service's `env_file: /home/nelson/containers/<service>/.env` convention should work unmodified. Worth flagging explicitly if a real migration ever proceeds: this mount is a **read-only** bind of the same directory Portainer already mounts read-write into itself for the same reason (Phase 2) — Komodo's Periphery doesn't need write access to host secrets files, only Portainer's own separate `/home/nelson/containers:/home/nelson/containers:ro` mount pattern was replicated here, not Portainer's actual permission level (worth double-checking Portainer's own mount is also read-only if this gets revisited — not verified in this pass).

**Cleanup NOT yet performed (deliberately, left live for inspection alongside the other two POC stacks):** the `komodo-stateful-poc` Stack/container, its backing `komodo-stateful-poc-legacy_data` volume, the `/home/nelson/containers/komodo-poc-stateful-test/.env` file, and the repo's `komodo-poc-stateful-test/docker-compose.yml`. The Periphery mount addition to `komodo/compose.yml`, however, is a keeper regardless of whether the rest of this stack is torn down — any future stateful POC work depends on it being there.
