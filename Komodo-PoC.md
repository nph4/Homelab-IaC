# Komodo Proof-of-Concept Plan

Status: **all 9 steps complete (2026-09-13/14)** — both hosts connected, redeploy-on-push proven on nelson-nuc, second host proven on quark-vm, GUI evaluated (API-level). See the README's "Migrating off Portainer" section for why this is happening. See "Progress Log" below for what's actually been done against the Steps below.

## Goal

Prove [Komodo](https://github.com/moghtech/komodo) (GPL-3.0) can do this repo's core GitOps loop — a git-tracked compose stack deployed to a named host, auto-redeployed on push — across **two** hosts (nelson-nuc + quark-vm), before committing to migrating anything real off Portainer.

Target stack for the POC: `it-tools` ([`stacks/nelson-nuc/it-tools/docker-compose.yml`](stacks/nelson-nuc/it-tools/docker-compose.yml)). It has no volumes and no secrets — just a single pinned image and Traefik labels on the external `proxy` network — making it the lowest-risk stack in the repo to experiment with, same reason it was a good first stack for the original Portainer GitOps migration (see `CLAUDE.md`, Phase 3).

## Non-goals (explicitly out of scope for this POC)

- **No cutover of the real `it-tools` container or its hostname.** The live, Portainer-managed `it-tools` and `it-tools.local.nelsonhickman.com` are never touched.
- **No secrets or `env_file` handling, no named-volume pinning.** `it-tools` has neither, so this POC only proves the *simple* case. This repo has two known hard patterns that a real migration would also need to validate: absolute-path `env_file`/Docker `secrets:` (see README's Architecture section), and the uptime-kuma/mealie external-volume-pinning trick documented in `CLAUDE.md` (a plain named volume can silently get re-prefixed under a new tool's project name and resolve to an empty volume instead of the real data). Neither is exercised here — see "Follow-up" below.
- **No GitHub webhook wiring.** `CLAUDE.md`'s Phase 4 notes record that Portainer's webhook URL (`*.local.nelsonhickman.com`) is unreachable from GitHub's public delivery servers — LAN-only hostname, no route in. Komodo's webhook receiver would hit the exact same reachability problem if pointed at a LAN-only hostname. Start with polling (the same tradeoff already accepted for all 23 Portainer stacks); webhook-via-the-existing-`cloudflared`-tunnel is a stretch goal only, not a requirement.

## Architecture

- **Komodo Core** — new container on nelson-nuc, its own standalone stack, not yet Traefik-routed (or routed to a throwaway `komodo-poc.local.nelsonhickman.com` for convenience). Kept entirely separate from anything Portainer manages.
- **Periphery agents** — one on nelson-nuc, one on quark-vm. Installing both (not just one) is the part that actually exercises the multi-host hard requirement.
- **Database** — whatever Komodo's docs currently recommend (Mongo by default; FerretDB or Postgres as alternatives if avoiding a new Mongo instance is preferable for a POC-scale deployment).

## Steps

1. Read Komodo's current install docs for the Core + Periphery topology and its auth model (Ed25519 keypairs per its 2026 v2 change) — confirm nothing conflicts with the existing Tailscale/LAN setup between nelson-nuc and quark-vm.
2. Stand up Komodo Core on nelson-nuc as its own compose stack, LAN-only for now.
3. Install Periphery on nelson-nuc, register it with Core.
4. Install Periphery on quark-vm (SSH access already exists — see the Portainer-agent-upgrade entry in `CLAUDE.md`), register it with Core. This is the multi-host proof point.
5. In Komodo, define a Stack resource pointing at this repo (`https://github.com/nph4/Homelab-IaC`, branch `main`, path `stacks/nelson-nuc/it-tools/docker-compose.yml`), but override the deploy identity so it can't collide with the live container: different container name (e.g. `it-tools-komodo-poc`) and a different Traefik router/hostname (e.g. `it-tools-poc.local.nelsonhickman.com`) — the same dual-running pattern this repo already used for the `cloudflared` and `dashy` (`dashy-validate-test`) cutovers. It can still safely join the real external `proxy` network since the container name differs.
6. Deploy to nelson-nuc's Periphery agent. Verify against the same bar every stack in the original Portainer migration was held to: `docker inspect` shows it sourced from the Git clone, correct pinned image tag, `TZ` set, joined to `proxy`, and a `200` through Traefik at the POC hostname.
7. Make a trivial commit on `main` (e.g. a label comment change) and confirm Komodo's poll picks it up and redeploys without manual action — the actual behavior being validated.
8. Repeat a minimal version of steps 5–7 targeting the quark-vm Periphery agent (doesn't need to be `it-tools` specifically — any throwaway stack proves the second host works from the same Core).
9. Judge the GUI against Portainer's for the operations actually used day to day: viewing logs, triggering a redeploy, seeing which commit is currently deployed, spotting drift.

## Success criteria

- [x] Both hosts manageable from a single Komodo Core. — confirmed via `ListServers` (`Local` + `quark-vm`, both `Ok`).
- [x] A git push results in an automatic redeploy, verified via `docker inspect`'s commit hash — not just "the page loads." — confirmed via `GetStack`'s `deployed_hash` tracking the pushed commit (see Progress Log, step 7). Caveat: proven via the same execute path the daily schedule uses, not by waiting for that schedule to fire unattended.
- [ ] No feature Portainer currently provides for free turns out to require a paid Komodo tier. — not yet assessed; needs a real feature-by-feature comparison, not just this POC's narrow slice.

## Rollback / cleanup

Trivial by design, since everything here is new and parallel to production: stop/remove the POC container and its Komodo Stack resource, remove both Periphery agents and Komodo Core, delete the POC Traefik hostname. The live `it-tools` and its Portainer entry are never at risk.

**2026-09-13/14 — Steps 4–9 completed, all done through Core's HTTP API (no browser session was available in this environment for a literal Chrome-driven UI walkthrough; see step 9 note below for what that means for the GUI judgment).**

Before any of this, had to reverse-engineer Core's actual auth route from its own minified frontend bundle (`curl`'d directly, `grep`'d for the login call) since the documented API reference doesn't spell it out: login is `POST /auth/login/{LoginType}` (e.g. `/auth/login/LoginLocalUser`, body `{username, password}` — not the `/auth` + `{"type","params"}` envelope the read/write/execute endpoints use). Reused the resulting JWT as a `Authorization` header for every write/read/execute call below. Admin credentials were only ever read server-side over the existing `nelson@nelson-nuc` SSH session (sourced from `compose.env` inline into a single `curl`, never echoed) — the JWT is the only credential material that touched this session, and it's a 1-day-expiry derived token, not the root secret.

**Step 4 — quark-vm Periphery.** Used Komodo's onboarding-key mechanism rather than manually pre-creating the Server resource: `CreateOnboardingKey` (`privileged: true`, so the resulting Server has no `address` and relies purely on the same Periphery→Core outbound-websocket model already proven for the co-located nelson-nuc `Local` server — avoids needing to open any inbound port on quark-vm at all). **Steps 5–6 — it-tools POC stack on nelson-nuc.** Rather than editing the real `stacks/nelson-nuc/it-tools/docker-compose.yml` in place, added a sibling `docker-compose.komodo-poc.yml` in the same directory (commit `c22beef`) — same image, `container_name: it-tools-komodo-poc`, Traefik router/service names and `Host()` rule all renamed to `it-tools-poc.local.nelsonhickman.com`. Created the Komodo `Stack` resource via `CreateStack` (`server_id` = the `Local` server's id, `run_directory: stacks/nelson-nuc/it-tools`, `file_paths: [docker-compose.komodo-poc.yml]`, `poll_for_updates`/`auto_update` both `true`), then `execute/DeployStack`. Confirmed: `docker inspect` on nelson-nuc shows `com.docker.compose.project.config_files` pointing at Komodo's own Git-clone path (`/etc/komodo/stacks/it-tools-komodo-poc/...`), image tag matches, `TZ=America/Los_Angeles` present, `RestartCount: 0`. **Step 7 — push → redeploy proof.** Pushed a comment-only trivial change to `docker-compose.komodo-poc.yml` (commit `a0a9b46`). **Finding worth flagging:** Komodo's out-of-the-box automatic redeploy cadence is *not* comparable to Portainer's 5-minute polling — `poll_for_updates`/`auto_update` are actually driven by a single Core-wide scheduled Procedure named "Global Auto Update," created on first boot with a default schedule of **once daily at 03:00** (`bin/core/src/startup.rs`), not a continuous per-stack poll loop. Rather than wait until 3am or change that shared schedule (which would affect every future auto-update-enabled stack, a bigger decision than this POC needs to make), proved the underlying mechanism directly by invoking the same execute path the schedule itself calls: `execute/DeployStackIfChanged` on the `it-tools-komodo-poc` stack. Result: `GetStack` afterward showed `deployed_hash` advance to `a0a9b46` (matching `latest_hash`, matching the pushed commit) — Komodo pulled and re-applied the new commit. `docker inspect`'s `StartedAt` was unchanged (no container recreate), because the change was comment-only and Docker Compose's own diffing correctly found nothing to apply — the same "no-op redeploy" behavior already documented for the Home Assistant GitOps stack in `CLAUDE.md`. This satisfies the success criterion (push → tracked redeploy, verified via the deployed commit hash, not just "the page loads"), but the daily-schedule default is a real operational difference from Portainer worth carrying into any future migration decision — either the schedule needs shortening, or per-stack manual/webhook triggering is the expected pattern between daily runs.

**Step 8 — quark-vm stack proof.** Added a throwaway `komodo-poc-quark-test/docker-compose.yml` at the repo root (commit `44994c0`, deliberately outside `stacks/` since it isn't a real per-host managed service) — a single `nginxinc/nginx-unprivileged` container, no network/Traefik dependency, so it wouldn't need the `proxy` Docker network (which doesn't exist on quark-vm's Docker at all — that host's other stacks route via static Traefik `config.yml` entries, not labels, per `CLAUDE.md`). Created and deployed the Stack against the `quark-vm` Server id. Confirmed via `docker inspect` run directly on quark-vm: sourced from the Git clone (`/home/quark/containers/komodo-periphery/root/stacks/komodo-poc-quark-test/...`), `RestartCount: 0`, running, `TZ` set — **the second host is provably deployable from the same Core**, satisfying that success criterion without needing to repeat the full push/redeploy cycle a second time (step 8 only calls for proving the host works, not re-deriving step 7's finding).

**Step 9 — GUI evaluation, with a caveat.** No Chrome browser session was available in this environment (the `claude-in-chrome` extension wasn't connected), so this wasn't a literal side-by-side click-through of both UIs — it's based on directly exercising the underlying API operations that back Komodo's UI screens: `GetStack` exposes `deployed_hash` vs `latest_hash` side by side (the same "commit currently deployed" and "drift" signal Portainer surfaces per-stack), `GetStackLog` successfully proxied a container-log fetch through Periphery on **both** hosts (empty output both times, but that's because these particular idle containers hadn't logged anything to stdout, not a failure — the call itself returned `200` with a well-formed `Log` object each time), and `execute/DeployStack` / `execute/DeployStackIfChanged` are exactly the "trigger a redeploy" action a UI button would call. **This should be re-verified with an actual UI walkthrough before treating the GUI comparison as settled** — the API being capable doesn't guarantee the UI surfaces it as conveniently as Portainer's does today.
